# 技术决策记录

> 记录项目发展过程中的关键技术选型及其理由。

---

## 1. WebSocket 仅信令

**决策**：WebSocket 仅处理信令（SDP/ICE/ping），业务消息全部走 WebRTC DataChannel。

**理由**：为互联网远程控制做准备。纯 WebRTC 方案下，WebSocket 只在 P2P 连接建立前使用，建连后所有消息走 DataChannel，延迟更低且天然支持 NAT 穿透。

**时间**：2025 年 5 月（项目初期）

---

## 2. STUN 穿透

**决策**：使用 Google 免费 STUN (`stun.l.google.com:19302`) 辅助 WebRTC NAT 穿透。

**理由**：局域网开发阶段无需 TURN 中继，STUN 足够处理大部分家庭 NAT 类型。生产环境需补充 TURN 服务器（见 R00036）。

**时间**：2025 年 5 月

---

## 3. DataChannel 可靠有序

**决策**：DataChannel 配置为 `ordered: true, maxRetransmits: null`（可靠有序模式）。

**理由**：控制指令必须保证顺序和送达（如紧急停止不可丢包）。牺牲极小延迟换取可靠性。未来高频遥测可单独开不可靠通道。

**时间**：2025 年 5 月

---

## 4. 队列缓冲

**决策**：DataChannel 未就绪时，业务消息暂存 `_pendingQueue`，open 后自动发送。

**理由**：WebRTC 建连有延迟（SDP 交换 + ICE 协商约 1-3 秒），期间到达的业务消息不应丢弃。

**时间**：2025 年 5 月

---

## 5. 持久 Shell CWD

**决策**：`message_handler._shell_cwd` 跟踪 SSH 执行器的当前工作目录。

**理由**：前端 SSH 终端需要保持 cd 状态，不能每次执行命令都重置目录。

**时间**：2025 年 6 月

---

## 6. 硬件抽象层

**决策**：`HardwareInterface` 支持 Mock / Serial / GPIO 三种后端，`MotionController` 通过抽象层发送轮速。

**理由**：开发调试时不依赖物理硬件（Mock），真机部署时通过配置切换（Serial/GPIO），代码层零改动。

**时间**：2025 年 6 月

---

## 7. WebSocket 认证

**决策**：支持 URL query `?token=xxx` 和首条 `auth` 消息两种认证方式，由 `security.auth_enabled` 开关控制。

**理由**：本地开发可关闭认证快速调试，生产环境启用 JWT Token 认证。两种方式兼容不同客户端接入方式。

**时间**：2025 年 6 月

---

## 8. 语音通话 PCM 直传

**决策**：通话模式使用 `AudioContext` + `ScriptProcessorNode` 从话筒捕获原始 PCM（s16le, 48kHz），通过 WebSocket 二进制直传机器人 aplay 播放。

**理由**：绕过 MediaRecorder/WebM/ffmpeg 编解码链路，消除以下问题：
- `ondataavailable` 分片数据不可靠（重复/丢帧）
- WebM header + Cluster 累积导致传输重复音频
- ffmpeg 子进程开消过大

**时间**：2026 年 6 月

---

## 9. 请求Token绑定安全机制

**决策**：客户端绑定采用 requestToken（HMAC-SHA256 签名）+ randomCode 二次验证机制。机器人将 requestToken 与 randomCode 绑定，其他客户端即使看到/听到 randomCode，因其 requestToken 不匹配也无法完成绑定。

**理由**：
- 所有认证方式（屏幕显示/TTS播报/云台转动/密码）共享同一安全流程
- randomCode 120 秒过期且一次性使用
- requestToken 由客户端用 clientId + nonce 生成 HMAC，机器人验证后绑定
- 绑定成功后返回 clientToken（ROBOT_SECRET 对 deviceId + clientId + timestamp 签名），后续免验证

**时间**：2026 年 7 月

---

## 18. 媒体文件 DataChannel 分块传输

**决策**：拍照/录像产出的媒体文件（JPEG/MP4）通过 WebRTC DataChannel 分块传输（每块 16KB），替代 HTTP API 下载方式。

**理由**：
- 移除 HTTP API 媒体端点依赖，统一走 WebRTC 通道，减少攻击面
- 前端无需管理额外的 HTTP URL，所有数据通过同一 DataChannel 流转
- 分块传输支持大文件（录制视频可达 60MB/段），支持进度跟踪
- 机器人端无需暴露额外 HTTP 端口

**时间**：2026 年 7 月 22 日

---

## 19. 循环录制策略

**决策**：录像采用循环录制模式：每 60 秒自动分段，最多保留 10 段（总约 10 分钟），超出后自动覆盖最早的段。前端断线时自动停止录制。

**理由**：
- Jetson 存储空间有限，无限制录制会快速占满磁盘
- 分段存储降低单文件损坏风险（某段损坏不影响其他段）
- 前端断线自动停止防止无人值守时的无效录制
- 10 段窗口覆盖绝大多数使用场景（遥控回放、异常记录）

**时间**：2026 年 7 月 22 日

---

## 20. wo-bot-market 双 Token 认证

**决策**：wo-bot-market API 支持两种认证方式：X-API-Token（市场自身签发的 token，用于机器人查询软件包）和 Authorization Bearer JWT（Logto 签发的用户 token，用于管理操作）。发布端点支持 X-API-Token 认证。

**理由**：
- API Token 用于机器人端自动查询，无需用户交互
- JWT 用于管理操作（发布软件包），绑定用户身份
- 为后续 API 限流和审计日志提供用户/机器维度的追踪能力
- 与 wo-bot-account 的 OIDC 体系对接，统一用户身份

**时间**：2026 年 7 月 26 日

---

## 21. 软件自升级 detached dpkg 安装

**决策**：wo-bot-control 自升级采用 detached 子进程方式执行 `dpkg -i`，升级完成后自动重启服务（systemctl restart）。

**理由**：
- dpkg 安装后触发 postinst 脚本 → systemctl daemon-reload，主进程不能直接执行会导致自身被终止
- detached 子进程独立于主进程生命周期，确保升级流程完整执行
- build-deb.sh 构建脚本标准化 .deb 包的版本号和依赖声明

**时间**：2026 年 7 月 26 日

---

## 22. OAuth 已授权应用跳过同意页面

**决策**：Logto 中已授权的 OAuth 应用在用户再次登录时自动跳过同意页面（consent screen），直接完成授权流程。

**理由**：
- 首次授权已确认过权限范围，重复展示同意页面无意义且影响体验
- 减少用户登录摩擦，加速设备绑定和云端远控的启动流程
- Logto 原生支持 `prompt=consent` 参数控制，通过配置实现无需修改源码

**时间**：2026 年 7 月 22 日

## 23. 跨项目 CI/CD 标准化

**决策**：所有 wo-bot 子项目统一接入 GitHub Actions CI/CD 流水线，覆盖代码规范检查（Python: ruff+mypy, TypeScript: ESLint, Node.js: ESLint）。

**理由**：
- wo-bot-account、wo-bot-signal、wo-bot-market 三个云端子项目先后完成 CI/CD 接入
- 统一的代码质量标准，避免不同项目风格不一致
- PR 时自动检查，减少人工 Code Review 负担
- 构建矩阵优化：移除 Logto 镜像构建，CI 构建从 3 镜像减为 2 镜像

**时间**：2026 年 7 月 19-26 日

## 24. 摄像头画面画质选择

**决策**：Web 端支持摄像头画面传输画质三档选择（高/中/低），通过修改 VP8 编码参数（bitrate/fps/resolution）实现。

**理由**：
- 不同网络条件下需要不同画质：局域网高画质（2Mbps/30fps），4G/5G 远程中等（1Mbps/15fps），弱网低画质（500kbps/10fps）
- 动态调整减少带宽消耗，延长移动端续航
- 画质参数存储在 config 中，机器人重启后保持

**时间**：2026 年 7 月 24 日

## 25. 声明式外设数据采集框架

**决策**：建立 `PeripheralRegistry` 声明式外设数据采集框架：平台定义标准数据槽位（温度、湿度、气体等），用户通过三种 provider 方式提供数据——`builtin`（平台内置驱动，如 DHT11）、`custom`（用户自写可执行程序，stdout 输出 JSON 契约）、`external`（外部数据源：HTTP/MQTT/文件/串口/WebSocket API），也可置空（`none`）表示无此硬件。

**理由**：
- 原 GPIO 外设接线全部硬编码在 Python 源码中（如 `DHT11_GPIO = 194`），换板子/换引脚必须改代码重新部署，严重影响通用性
- 声明式 YAML 配置（`peripherals.yaml`）与代码解耦，社区适配只需改配置，无需修改平台源码
- 三种 provider 抽象覆盖所有数据获取场景：平台内置传感器驱动、用户自定义采集脚本、外部 IoT 数据源接入
- 每个槽位独立配置、独立采集、互不影响；采集失败时保留上次有效值（缓存策略），不掉为 None
- 在线判断基于最后成功时间（容忍偶发失败，interval × 3 内视为在线），状态随 WebSocket status 消息推送前端

**时间**：2026 年 7 月 29 日

## 26. SQLite 传感器时序数据存储与双 Y 轴可视化

**决策**：基于 R00044 采集框架产出的传感器数据，使用 SQLite（`data/peripherals.db`）持久化存储，前端使用 ECharts 实现多传感器双 Y 轴时间轴图表展示。

**理由**：
- SQLite 零运维、Jetson 原生支持、单文件部署，适合嵌入式设备的时间序列存储
- 存储结构 `{slot_name, timestamp, value, value_json, unit}` + 复合索引 `(slot_name, timestamp)`，查询高效
- 批量写入策略：每个采集周期批量 INSERT 一条 SQL，减少 I/O；DHT11 等复合传感器 `value_json` 保存完整 JSON 供特殊查询
- 数据保留策略：可配置保留天数（默认 7 天），定时自动清理过期数据，防止磁盘占满
- ECharts 双 Y 轴方案：不同传感器（温度°C、湿度%）各自独立 Y 轴缩放，避免数值范围差异导致单轴无法同时展示
- HTTP API `GET /api/peripherals/history?slots=dht11&range=1h`，前端按需拉取，不占 WebSocket 带宽

**时间**：2026 年 7 月 29 日

## 27. UART 串口红外学习模块替代软件 Bitbanging

**决策**：红外遥控采用智家物联科技红外学习模块（UART 串口通信，115200bps 8N1），替代 Jetson GPIO 软件 bitbanging 方案。模块内置单片机硬件生成 38kHz 载波，支持学习（自动压缩波形编码）和发射功能，7 组内部存储（每组 512B）+ 外部存储（800B）。

**理由**：
- 软件 bitbanging 实测周期偏差 ±50%（14kHz~61kHz），家电红外接收头拒收；Jetson 无硬件 PWM 可用（pinmux 冲突）
- 串口模块方案精度 <±0.5%、CPU 零开销、成本极低（~10 元）、串口编程成熟
- 码库存储：JSON 按设备分文件，动态分配模块内部存储索引（0~6），支持码库导入/导出
- WebSocket 消息协议：13 种消息类型覆盖设备CRUD/学习/发射/导入导出全流程
- 云端码库（IRDB/LIRC/Flipper-IRDB）对风扇等小众品类覆盖极差，当前阶段以学习模块直接抓码为主

**时间**：2026 年 8 月 3 日

## 28. 摄像头热恢复机制

**决策**：`camera.py` 新增摄像头热恢复逻辑：当摄像头进程异常断开（USB 松动、进程崩溃等）时，自动检测并重新初始化摄像头流，无需手动重启服务。

**理由**：
- Jetson 的 USB 摄像头在物理震动或电压波动时可能出现短暂的断开重连
- 热恢复机制避免用户因摄像头断开而必须 SSH 登录机器人重启服务
- 恢复流程：捕获 GStreamer 管道异常 → 等待摄像头设备重新出现 → 重新初始化管道 → 通知前端视频流恢复

**时间**：2026 年 8 月 3 日

## 15. 放弃 Fork Logto，改用官方 Docker 镜像

**决策**：授权服务放弃 Fork Logto 源码仓库的方案，改用官方 Docker 镜像 `ghcr.io/logto-io/logto`，所有定制通过运行时配置完成。

**理由**：
- Logto 官方提供了丰富的运行时配置能力（品牌定制、SMTP、CAPTCHA、sign-in-exp 等），无需修改源码
- Fork 源码维护成本高（git subtree 合并、解决冲突、重新构建镜像），改为官方镜像后版本升级只需修改 tag + 拉取新镜像
- CI/CD 构建矩阵从 3 个镜像减为 2 个（移除 logto 镜像构建），加速构建
- 移除 `logto/` 目录和 `scripts/sync-logto-upstream.sh`，仓库结构更简洁

**时间**：2026 年 7 月 18 日

## 16. 管理后台与授权服务解耦

**决策**：将 R00040 用户帐号服务器拆分为四个独立子需求（R00040-1 管理后台、R00040-2 授权服务选型、R00040-3 部署实施、R00040-4 管理面安全访问），管理后台的业务逻辑不依赖特定授权服务，通过标准 OIDC 协议消费任意授权服务签发的 JWT。

**理由**：
- 原 R00040 将"管理后台业务逻辑"和"授权服务选型"混合在一个文档中，导致二者在概念上耦合
- 管理后台（R00040-1）定义与授权服务交互的标准接口（OIDC Discovery / JWKS / UserInfo），不绑定 Logto
- 授权服务（R00040-2）作为可替换的实现，当前选择 Logto，未来可切换为 Casdoor、Zitadel 等
- 服务路由使用三域名架构：`user.{domain}`（用户侧页面）、`api.{domain}`（管理 API）、`admin.{domain}`（管理控制台）
- 部署层（R00040-3）统一编排，通过 Caddy 反向代理按路径分流

**时间**：2026 年 7 月 18 日

## 17. Logto Admin Console 独立子域名 + 六层纵深防护

**决策**：将 Logto Admin Console 从 `user.{domain}/admin` 迁移到独立子域名 `admin.{domain}`，叠加六层纵深防护：Cloudflare Zero Trust Access → WAF IP 白名单 → Logto OIDC 认证 → 网络层端口隔离 → 独立 TLS 证书 → 访问审计日志。

**理由**：
- 管理流量与用户流量分离，可对管理面单独施加更严格的访问限制
- Cloudflare Zero Trust Access 替代 Basic Auth：标准登录页面（所有浏览器通用）、支持 MFA/SSO、凭证不出现在 URL、边缘拦截恶意流量不到达源站
- Basic Auth 的 URL 内嵌凭证问题导致密码泄露到浏览器历史、Referer、服务器日志，且 Trae/Electron 内置浏览器不支持 Basic Auth 弹窗
- 独立审计日志（`/data/caddy/logs/admin-access.log`）记录真实客户端 IP，便于异常访问追溯

**时间**：2026 年 7 月 19 日

## 10. 外设检测与多方式认证

**决策**：`PeripheralDetector` 检测可用外设（显示器/摄像头/音频/云台），按优先级返回认证方式列表。客户端展示排序后的选项给用户选择。

- 密码绑定作为兜底方案，配置控制开关

## 11. 软件包白名单管理

**决策**：通过 wo-bot-market 子项目提供 manifest.json 白名单，wo-bot-control 启动时拉取。仅允许操作白名单内的官方软件（升级/卸载/安装），系统其他软件提示使用终端。

- 市场服务器独立部署在开发电脑，机器人仅 HTTP 拉取元数据

## 12. 日志增量同步

**决策**：日志面板采用基于行号游标的增量同步协议（tail/since/before 三种模式），替代全量拉取。

**理由**：
- tail：首次加载取最新 N 条
- since：轮询只拉取游标之后的新日志，避免重复传输
- before：滚动到顶部时加载更早的历史日志
- 清空后游标重置为当前服务端行数，只显示新日志
- 断点续传：网络恢复后自动补拉积压日志

**时间**：2026 年 7 月

## 14. 预生成音频资产

**决策**：寻找设备提示音采用预生成方波 wav 文件（1318Hz E6 正弦波 + 2倍频谐波 + 快速衰减包络），打包为 `assets/wobot_beep.wav`，运行时直接 aplay 播放。

**理由**：避免运行时 ffmpeg 动态生成音频（子进程开销 + 音量不可靠），预生成文件确保音色和音量一致。三声短促"叮叮叮"手机通知音风格，用户确认满意。

**时间**：2026 年 7 月
