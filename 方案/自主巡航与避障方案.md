> 状态：🔵 设计阶段（方案已定，待评审） | 最后更新：2026-10-07
> 关联需求：R00049 ｜ 关联路线图：T042 / T045-B / T046
> 迭代排期见 [自主巡航迭代规划.md](自主巡航迭代规划.md)

---

## 一、目标与非目标

### 目标

| 模式 | 一句话定义 | 用户期望 |
|---|---|---|
| **半自动（semi）** | **人管方向，机管不撞** | 用摇杆操控，机器人有权限速/横移绕行/急停，但不会自己选路 |
| **全自动（auto）** | **机管路线与安全** | 机器人按预设航线自主巡航，途中自主避障、到点停靠，人可随时接管 |

同时建立一套**可复用的分层架构**（感知 → 定位 → 决策 → 执行 → 安全），
后续的巡逻、场景联动、定时任务都建立在它之上。

### 非目标（本阶段明确不做）

- **全屋 SLAM 建图与长期全局定位** —— 需要 2D/3D 雷达，属 T042 的完整形态，放在雷达到位之后
- 跨房间长距离导航、上下台阶、电梯
- 语义级任务理解（"去厨房拿水"）
- 高速运动（本阶段速度上限保守，安全优先）

## 二、现状勘察（真机实测）

### 2.1 硬件能力

| 能力 | 状态 | 证据（实测） |
|---|---|---|
| 底盘 | **麦克纳姆轮，原生三轴** | Rosmaster_Lib 提供 `set_car_motion`；代码已有 `set_mecanum_velocity(v_x, v_y, v_z)` |
| 里程计 | ✅ **电机编码器可读** | `get_motor_encoder` |
| 姿态 | ✅ **9 轴 IMU** | `get_accelerometer_data` / `get_gyroscope_data` / `get_magnetometer_data` |
| 电池 | ✅ 电压可读 | `get_battery_voltage`（`collector.py` 已在用） |
| 视觉 | ✅ 2 路 | USB 彩色 + CSI(imx219)，本会话已修复 |
| 云台 | ✅ PWM + UART 舵机 | `gimbal.py` |
| 人机提示 | ✅ 蜂鸣器 + 彩色灯 | `set_beep` / `set_colorful_lamps` |
| **测距** | ❌ **完全没有** | 全库扫描 `ultrason/tof/lidar/distance/sonar` **零命中**（仅有 `range()` 循环误报） |

序列通信：`/dev/ttyUSB0`（CH340，`1a86:7523`）↔ Rosmaster 扩展板。
I2C 总线 `i2c-0/1/3/…/8` 空闲可用（`i2c-7/8` 上 0x10/0x40 已被 CSI 摄像头占用）。

### 2.2 算力现状（关键约束）

```
CPU  [70%@1479, 72%@1479, 71%@1479, 63%@1479]   ← 四核已在 70% 上下
RAM  2040/3964MB（可用 ~1.8G）
GR3D_FREQ 0%                                    ← GPU 完全空闲
```

- **CPU 是瓶颈，GPU 是空白** → 视觉推理应走 **TensorRT/GPU**，决策逻辑必须轻量
- 桌面合成器 `compiz` 曾长期占用 70–80% CPU，是最大的可回收算力（见风险 R5）

### 2.3 软件现状

| 项 | 现状 | 结论 |
|---|---|---|
| 运动控制 | `MotionController`：`set_velocity` / `set_mecanum_velocity` / `stop` / `emergency_stop` | 执行层已具备，可直接复用 |
| 硬件层 | `RosmasterHardware` 已创建接收线程（`create_receive_threading`） | 串口通道就绪，读 IMU/编码器无需新增连接 |
| 控制模式 | 前端有 `ControlMode = "manual" \| "semi" \| "auto"` 选择器 | **服务端零处理**（`grep control_mode` 无结果）→ 纯空壳 UI |
| 传感器采集 | `collector.py` 仅读电池电压 | IMU / 编码器**尚未读取** |
| 里程计/位姿 | **无任何 odom/pose 概念** | 需新建 |

> 结论：**执行层和通信层可直接复用，感知与决策层需要从零建设。**

## 三、技术路线选型

### 3.1 为什么不能"只靠视觉避障"

直觉方案是"用摄像头识别障碍物"，但在本平台上不可单独作为安全依据：

| 问题 | 说明 |
|---|---|
| 测距精度 | 单目视觉无法给出可靠的真实距离，只能给相对/启发式深度 |
| 漏检场景 | 玻璃、纯白墙、深色地毯、逆光、低矮桌沿/线缆 —— 恰好是"最该躲开"的 |
| 算力预算 | CPU 已 70%，视觉推理若走 CPU 会直接挤垮 WebRTC 与云台控制 |
| 安全等级 | 避障是**安全功能**，不能建立在"大概率能识别"的统计模型上 |

**因此：近距离可靠测距必须有专用传感器；视觉用于补充远场与低矮/透明障碍。**

### 3.2 传感器补充建议（按性价比排序）

| 方案 | 成本 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| **I2C TOF（VL53L1X）** ×2~3 前/左/右 | ¥15–30/个 | 毫米级、不受光照/颜色影响、**不依赖 Rosmaster 固件**（直接挂 Jetson I2C）、体积小 | 视场角窄（~27°），强日光下量程下降 | ⭐ **首选** |
| 超声波（HC-SR04）×2 | ¥5 | 便宜、对软质/深色物体稳定、量程 ~4m | 需 2 个 GPIO + 计时、响应慢、易受气流/回声干扰 | ⭐ 辅助（补 TOF 盲区） |
| 2D 雷达（RPLIDAR A1 级） | ¥300–600 | 360° 扫描、可做 SLAM/建图 | 成本高、需完整 SLAM 栈、算力占用大 | ⏳ **推迟到 Step 3 定位/建图阶段** |
| 深度相机（RealSense 等） | ¥1000+ | 直接给深度图 | 成本最高、USB 带宽/算力压力大 | ❌ 暂不考虑 |

> **建议先上 2–3 个 VL53L1X**（约 ¥50–90），即可覆盖前向与侧向近场，是投入产出比最高的一步。
> 40-pin 排针被 Rosmaster HAT 占用，I2C 引出位置需物理确认（见未决问题 U1）。

### 3.3 定位方案：轮式里程计 + IMU 融合（**不做 SLAM**）

```
编码器四轮脉冲 ──► 轮式里程计 ─┐
                              ├─► 互补滤波 / 轻量 EKF ──► (x, y, θ)
陀螺仪 Z 轴角速度 ────────────┘
磁力计 ──► 绝对航向校正（仅在干扰小的区域启用）
```

- **为什么可行**：短距离（单房间内、几米尺度）巡航对定位精度要求不高；
  主要用途是"沿直线走、到点停、能原路返回"，误差容忍度在 20–30cm 级。
- **诚实说明其局限**：麦克纳姆轮**横向打滑严重**，纯里程计会持续漂移；
  这是**相对定位**，不能承诺"长期知道自己在全屋哪个位置"。
- **漂移的兜底手段（按需启用）**：视觉路标（地面/墙面标记）、
  回充座/固定信标的接近信号、**用户手动"在此处校正"**。

### 3.4 避障策略：分层反应式（不追求全局最优路径）

| 层 | 频率 | 职责 | 传感器 | 优先级 |
|---|---|---|---|---|
| **L1 反射层** | 100–1000Hz | 距离 < 急停阈值 → **直接刹车** | TOF/超声 | **最高**（可越过决策层） |
| **L2 反应层** | 10–20Hz | 扇区化减速、**横移绕行**（麦轮优势）、贴边行驶 | TOF/超声 | 高 |
| **L3 规划层** | 1–5Hz | waypoint 巡线 + 局部代价地图（轻量 VFH / 势场法） | 定位 + L2 汇总 | 中 |
| **L4 视觉层** | 2–10Hz | 远场障碍、低矮/悬空、透明物体、地面可通行区域 | 摄像头（GPU/TRT） | 补充 |

**麦轮是重要优势**：遇到障碍可以不减速直接**横向平移**让开，比差速底盘动作更自然。

## 四、架构设计

### 4.1 模块划分（落在 `wo-bot-control`）

```
src/modules/navigation/            ← 新建
├── odometry.py          里程计：编码器 + IMU 融合 → (x, y, θ, v, ω)
├── safety.py            安全仲裁：反射层急停、看门狗、失效策略（最高优先级）
├── avoidance.py         避障：传感器扇区 → 限速/绕行矢量
├── planner.py           航线规划：waypoint 执行、到点判定、局部绕障
├── mode_manager.py      模式状态机：manual / semi / auto 与接管规则
└── sensors/
    ├── base.py          测距传感器抽象（可插拔：TOF / 超声 / 雷达）
    ├── tof_vl53l1x.py   I2C TOF 驱动
    └── ultrasonic.py    GPIO 超声波驱动（可选）
```

复用现有：
- 执行 → `motion/controller.py` 的 `set_mecanum_velocity` / `stop` / `emergency_stop`
- 通信 → `motion/hardware.py` 的 `RosmasterHardware`（串口线程已就绪）
- 上报 → `system/collector.py`（新增 odom / imu / 避障状态字段）

### 4.2 数据流

```
                    ┌──────────── safety.py（L1，独立协程，最高优先级）────────────┐
TOF/超声 ──扇区──► │  距离 < 急停阈值 → 直接调 controller.stop()，不经决策层        │
                    └───────────────────────────────┬────────────────────────────┘
                                                    │ 覆盖/否决
编码器 + IMU ──► odometry.py ──(x,y,θ)──► planner.py ──(vx,vy,vz 期望)──► avoidance.py ──► controller.set_mecanum_velocity
                       │                      ▲                                  ▲
                       └──► collector 上报    └── waypoint 航线（来自 Web 端）    └── 视觉层（L4）
摇杆（manual/semi）──────────────────────────────────────────────────────────────┘
```

### 4.3 协议扩展（草案）

| 消息 | 方向 | 说明 |
|---|---|---|
| `control_mode_set` / `control_mode_ack` | 前端 → 服务端 | 切换模式（**需鉴权**，见安全） |
| `control_mode_status` | 服务端 → 前端 | 当前模式、是否被安全层降级、降级原因 |
| `waypoint_list_set` / `waypoint_list_get` | 双向 | 航线增删改查 |
| `cruise_start` / `cruise_pause` / `cruise_resume` / `cruise_stop` | 前端 → 服务端 | 巡航控制 |
| `cruise_status` | 服务端 → 前端 | 当前航点、剩余距离、进度、避障事件 |
| `odometry_status` | 服务端 → 前端 | `(x, y, θ)`、速度、定位置信度 |
| `range_status` | 服务端 → 前端 | 各方向测距值（用于 Web 端可视化） |
| `avoidance_event` | 服务端 → 前端 | 触发减速/绕行/急停的事件与原因 |

> 状态类消息统一走现有的状态广播周期（复用 `collector` 的推送通道），避免高频刷屏。

## 五、模式定义与职责边界

### 5.1 权威定义

| | **manual** | **semi** | **auto** |
|---|---|---|---|
| 方向来源 | 摇杆 | 摇杆（人的**意图**） | 航线规划器 |
| 速度上限 | 人给多少给多少 | 避障层**可下调** | 规划器统一限速 |
| 避障动作 | 仅 L1 急停 | L1 急停 + L2 减速/横移绕行 | L1 + L2 + L3 局部重规划 |
| 会自己选路吗 | 不会 | **不会**（只做让开，不改变前进方向） | 会（在航线附近重规划） |
| 失效/超时 | 停车 | 停车 | 停车 + 上报 |

### 5.2 状态机与接管规则

- `manual → semi/auto`：需要显式请求 + **确认**（UI 二次确认，防止误触）
- `auto ⇄ semi`：允许直接切换；`auto → semi` 时**保留当前位置**，方向权立即交还给人
- `任意 → manual`：**立即生效**，机器人停车并把控制权交还（最高优先级，不受安全层阻塞）
- **安全层降级**：`semi/auto` 期间若触发多次急停或传感器失效 → 自动降级到 `manual` 并
  通过 `control_mode_status` 广播原因（**降级必须让用户知道**，不能静默）

## 六、安全设计（本方案的核心）

> 自主运动是**唯一可能造成物理损伤**的功能，安全设计先于功能。

| 层级 | 机制 | 触发 | 动作 |
|---|---|---|---|
| S1 | 反射层急停 | 前方距离 < 急停阈值 | 立即 `stop()`，最高优先级 |
| S2 | 传感器失效 | 读不到值 / 值异常（0 或超量程） | **按"有障碍"处理**（fail-safe），停车 |
| S3 | 决策层看门狗 | 决策协程 > 500ms 未心跳 | 停车 + 上报 |
| S4 | 通信失联 | 前端 WebSocket 断开 | 停车（不继续自驾） |
| S5 | 电池低压 | 电压 < 阈值（复用 `power_policy`） | 停止巡航 → 就近停靠 + 提示 |
| S6 | 姿态异常 | IMU 倾角超阈值 / 加速度冲击 | 停车（疑似跌落/被搬动） |
| S7 | 堵转/顶死 | 编码器反馈与指令长期不符 | 停车 + 反转脱离（可配置） |

**默认关闭**：`semi/auto` 默认禁用，需在配置中显式开启并在 UI 二次确认。
**一键急停**：UI 已存在，本方案把它接到 `emergency_stop()` 并保持最高优先级。

## 七、风险与未决问题

| ID | 风险/问题 | 影响 | 对策 |
|---|---|---|---|
| R1 | 麦克纳姆轮里程计漂移 | 巡航偏差累积 | 保守速度、短航程、手动校正点；不承诺长期定位 |
| R2 | **测距传感器尚未采购** | S2 之后全部迭代受阻 | 先做不依赖传感器的 S0/S1；尽快确认采购（见 U1） |
| R3 | CPU 已 70%，导航叠加算力 | 影响视频/控制实时性 | 决策层轻量化；视觉走 GPU；回收 `compiz` 算力 |
| R4 | 视觉避障误报/漏报 | 误刹或碰撞 | 视觉只做**补充**，安全兜底仍由 TOF 承担 |
| R5 | 桌面合成器占 70–80% CPU | 算力被白白吃掉 | 若机器人无需本地桌面 → 关闭（需用户确认） |
| R6 | Rosmaster 固件能力未知 | 编码器精度/堵转反馈可能不足 | S0 先实测编码器分辨率和一致性 |
| U1 | **40-pin 排针被 Rosmaster HAT 占用，I2C 引出位置需物理确认** | 决定 TOF 能否接入 | 需你在硬件上确认可用引脚；备选：HAT 的 I2C 扩展口 / USB-TOF |
| U2 | 是否接受加装传感器（¥50–90） | 决定技术路线 | **待你决策**（详见迭代规划 S2 的决策门） |
| U3 | 巡航的安全责任边界（人在不在场） | 影响速度/兜底策略 | 需明确使用场景 |
