## 一、目标与非目标

### 目标

| 模式 | 一句话定义 | 用户期望 |
|---|---|---|
| **半自动（semi）** | **人管方向，机管不撞** | 用摇杆操控，机器人有权限速/横移绕行/急停，但不会自己选路 |
| **全自动（auto）** | **机管路线与安全** | 机器人按预设航线自主巡航，途中自主避障、到点停靠，人可随时接管 |

同时建立一套**可复用的分层架构**（感知 → 定位 → 决策 → 执行 → 安全），
后续的巡逻、场景联动、定时任务都建立在它之上。

### 非目标（本阶段明确不做）

- **全屋 SLAM 建图与长期全局定位** —— 需要 2D/3D 雷达，属 T042 的完整形态，放在雷达到位之后
- 跨房间长距离导航、上下台阶、电梯
- 语义级任务理解（"去厨房拿水"）
- 高速运动（本阶段速度上限保守，安全优先）

## 二、现状勘察（真机实测）

### 2.1 硬件能力

| 能力 | 状态 | 证据（实测） |
|---|---|---|
| 底盘 | **麦克纳姆轮，原生三轴** | Rosmaster_Lib 提供 `set_car_motion`；代码已有 `set_mecanum_velocity(v_x, v_y, v_z)` |
| 里程计 | ✅ **电机编码器可读** | `get_motor_encoder` |
| 姿态 | ✅ **9 轴 IMU** | `get_accelerometer_data` / `get_gyroscope_data` / `get_magnetometer_data` |
| 电池 | ✅ 电压可读 | `get_battery_voltage`（`collector.py` 已在用） |
| 视觉 | ✅ 2 路 | USB 彩色 + CSI(imx219)，本会话已修复 |
| 云台 | ✅ PWM + UART 舵机 | `gimbal.py` |
| 人机提示 | ✅ 蜂鸣器 + 彩色灯 | `set_beep` / `set_colorful_lamps` |
| **测距** | ❌ **完全没有** | 全库扫描 `ultrason/tof/lidar/distance/sonar` **零命中**（仅有 `range()` 循环误报） |

序列通信：`/dev/ttyUSB0`（CH340，`1a86:7523`）↔ Rosmaster 扩展板。
I2C 总线 `i2c-0/1/3/…/8` 空闲可用（`i2c-7/8` 上 0x10/0x40 已被 CSI 摄像头占用）。

### 2.2 算力现状（关键约束）

```
CPU  [70%@1479, 72%@1479, 71%@1479, 63%@1479]   ← 四核已在 70% 上下
RAM  2040/3964MB（可用 ~1.8G）
GR3D_FREQ 0%                                    ← GPU 完全空闲
```

- **CPU 是瓶颈，GPU 是空白** → 视觉推理应走 **TensorRT/GPU**，决策逻辑必须轻量
- 桌面合成器 `compiz` 曾长期占用 70–80% CPU，是最大的可回收算力（见风险 R5）

### 2.3 软件现状

| 项 | 现状 | 结论 |
|---|---|---|
| 运动控制 | `MotionController`：`set_velocity` / `set_mecanum_velocity` / `stop` / `emergency_stop` | 执行层已具备，可直接复用 |
| 硬件层 | `RosmasterHardware` 已创建接收线程（`create_receive_threading`） | 串口通道就绪，读 IMU/编码器无需新增连接 |
| 控制模式 | 前端有 `ControlMode = "manual" \| "semi" \| "auto"` 选择器 | **服务端零处理**（`grep control_mode` 无结果）→ 纯空壳 UI |
| 传感器采集 | `collector.py` 仅读电池电压 | IMU / 编码器**尚未读取** |
| 里程计/位姿 | **无任何 odom/pose 概念** | 需新建 |

> 结论：**执行层和通信层可直接复用，感知与决策层需要从零建设。**

## 三、技术路线选型

### 3.1 先说结论：**采用纯视觉方案**（TOF 未落地）

原方案把"加装 TOF"作为首选。在实际确认**TOF 尚未实现**后，重新评估如下：

> **纯视觉可行 —— 但必须换一套技术路线与验收标准。**
>
> 关键认知转换：避障真正需要的不是"毫米级距离"，而是
> **"还要多久会撞上"（time-to-contact, TTC）与"哪个方向是通的"**。
> TOF 给前者的是距离，**单目视觉给前者的是 TTC —— 两者都能用于"该不该停"**。
> 一旦接受这个转换，纯视觉就从"勉强能用"变成"路线清晰"。

### 3.2 平台事实：**只能走经典 CV，不能走深度学习**（实测）

| 运行时 | 状态 |
|---|---|
| `cv2` 4.13.0 | ✅ 可用，但 **`cv2 build has CUDA: NO`**（pip 版，无 GPU 加速） |
| `tensorrt` / `onnxruntime` / `torch` / `pycuda` | ❌ **全部未安装** |
| `calcOpticalFlowPyrLK` / `goodFeaturesToTrack` / `findHomography` / `remap` / `initUndistortRectifyMap` | ✅ **全部可用** |
| CPU | 四核已 ~70% 占用 |
| GPU | 0% 空闲，但**当前 Python 环境没有任何 GPU 推理通路** |

**结论**：深度学习（YOLO/MiDaS/深度估计）在本平台**当前跑不起来** ——
不是模型不行，而是缺 TensorRT/onnxruntime/CUDA 版 OpenCV，而 Python 3.7 + L4T R32.7 上
装通这条链路本身就是一次独立的技术预研（见迭代规划 **S2-P**）。
**因此纯视觉路线采用经典 CV**，它所需的函数一个不缺。

### 3.3 纯视觉技术路线（四层，按落地顺序）

| 层 | 方法 | 输出 | 频率 | 用途 |
|---|---|---|---|---|
| **V1 光流发散 / TTC** | 稀疏光流（`calcOpticalFlowPyrLK`）+ **IMU 陀螺补偿旋转** → 计算发散度 | **TTC（秒）** | 10–20Hz（160×120 低分辨率） | **安全反射层**：TTC < 阈值 → 刹车（替代 TOF 的急停角色） |
| **V2 地面平面几何** | 相机标定（内参 + 高度/俯仰）→ 地面单应 → 自由空间走廊 | **可通行区域 + 低矮障碍/落差** | 5–10Hz | 低矮桌沿、线缆、台阶、悬空障碍 |
| **V3 云台主动扫视** | 云台摆动产生**运动视差**，近处物体在图像中位移更大 | **远近排序（非精确距离）** | 按需（停车/起步前） | 补偿"静止时无光流"的盲区 |
| **V4 语义检测** | 小模型目标检测（人/宠物） | 类别 + 框 | 低 | "人群避让"，**非安全兜底**。**依赖 S2-P 预研结果** |

**两个关键平台优势（值得利用）**

1. **有 IMU 陀螺** → 可以减去旋转引起的整体光流，这是让单目光流可用于 TTC 的经典前提。
   **本机恰好具备**，比一般单目方案条件更好。
2. **有可编程云台** → 可做"停下→扫视→再走"的主动视觉，用运动视差弥补静止盲区；
   巡航时也可小幅摆动扩大有效视野。

### 3.4 纯视觉的能力边界（必须接受的硬限制）

| 场景 | TOF | 纯视觉 | 后果 |
|---|---|---|---|
| 正常照明、有纹理 | ✅ | ✅ **TTC 可用** | 可正常避障 |
| **暗光 / 全黑** | ✅ 可用 | ❌ **完全失效** | 机器人**无任何照明硬件**（无红外补光）→ 暗处不可用 |
| **玻璃 / 纯白墙 / 无纹理** | ✅ 可用 | ⚠️ 特征缺失 → **只能保守判断** | 按"可能挡路"处理 → **停车**，不误判为可通行 |
| 静止障碍 + 机器人静止 | ✅ 可用 | ⚠️ 无运动视差 → 无法测距 | 靠 V3 云台扫视缓解 |
| **极近距（< 10cm）** | ✅ | ❌ 盲区较大 | 速度上限必须更低、安全余量更大 |
| 运动中的动态障碍（人/宠物） | ✅ | ⚠️ 需 V4，且当前无推理运行时 | 暂不做"人群避让" |

**由此带来的强制约束（写进验收与产品定义）**

- **auto 模式必须有环境限定**：仅限**有照明**、地面纹理正常的环境；
  **暗光下必须禁用 auto 或强制降到 crawl 速度**
- **速度上限显著低于 TOF 方案**（建议首版 ≤ 0.15–0.2 m/s，安全余量换掉测距精度）
- **纯视觉达不到"毫米级距离"验收** → 验收改为 **TTC / 停车距离 / 误刹率 / 降级行为**

### 3.5 关于"用两个摄像头做双目"

机器人确实有两个摄像头（USB + CSI），理论上可做双目立体测距。但**不推荐作为主路线**：

| 问题 | 说明 |
|---|---|
| 光学不一致 | 两颗摄像头型号、镜头、FOV 都不同，无法直接做极线校正匹配 |
| 基线极短 | 两摄相邻安装，短基线 → 远处深度误差急剧恶化 |
| 帧不同步 | CSI 走 `gst-launch` 子进程写 JPEG 文件，与 USB 的 V4L2 通路无法硬件同步 |
| 代价 | 需要完整双目标定 + 实时校正 + 立体匹配，属中等规模专题 |

> 若将来要做，建议**换用一对同型号摄像头**并做正规双目标定，而不是拿现在这两颗凑。

### 3.6 TOF 的定位：**可选增强，不是前置依赖**

TOF 从"首选前置"调整为**可选增强**：

- 架构上保留 **可插拔测距抽象**（`sensors/base.py`），将来接入 TOF/超声**不需要返工**
- TOF 一旦接入，能补上纯视觉最致命的两个短板：**暗光可用** 与 **近距无盲区**
- 成本仍很低（¥50–90），若后续愿意加装，收益立竿见影

| 方案 | 成本 | 相对纯视觉的价值 | 建议 |
|---|---|---|---|
| **纯视觉**（当前路线） | ¥0 | 主路线；暗光/近距受限 | ⭐ **现在就走** |
| I2C TOF（VL53L1X）×2~3 | ¥50–90 | **补暗光 + 近距盲区**，安全等级提升一档 | ⭐ 建议后续加装（不阻塞） |
| 超声波（HC-SR04）×2 | ¥5–10 | 同上，更便宜但更粗糙 | 可选 |
| 2D 雷达 | ¥300–600 | 360° + SLAM 建图 | ⏳ 推迟到 Step 3 定位/建图 |
| 深度相机 | ¥1000+ | 直接深度图 | ❌ 暂不考虑 |

### 3.3 定位方案：轮式里程计 + IMU 融合（**不做 SLAM**）

```
编码器四轮脉冲 ──► 轮式里程计 ─┐
                              ├─► 互补滤波 / 轻量 EKF ──► (x, y, θ)
陀螺仪 Z 轴角速度 ────────────┘
磁力计 ──► 绝对航向校正（仅在干扰小的区域启用）
```

- **为什么可行**：短距离（单房间内、几米尺度）巡航对定位精度要求不高；
  主要用途是"沿直线走、到点停、能原路返回"，误差容忍度在 20–30cm 级。
- **诚实说明其局限**：麦克纳姆轮**横向打滑严重**，纯里程计会持续漂移；
  这是**相对定位**，不能承诺"长期知道自己在全屋哪个位置"。
- **漂移的兜底手段（按需启用）**：视觉路标（地面/墙面标记）、
  回充座/固定信标的接近信号、**用户手动"在此处校正"**。

### 3.4 避障策略：分层反应式（不追求全局最优路径）

> 纯视觉路线下，**安全反射层由 V1（光流发散 / TTC）承担**；V2 负责低矮与落差；
> V3 补静止盲区；将来若有 TOF，则作为额外的一路感知源接入同一套风险扇区。

| 层 | 频率 | 职责 | 感知来源 | 优先级 |
|---|---|---|---|---|
| **L1 反射层** | 10–20Hz（视觉）<br>100–1000Hz（若有 TOF） | **TTC / 距离 < 阈值 → 直接刹车** | **V1 光流发散**（+ TOF 如有） | **最高**（可越过决策层） |
| **L2 反应层** | 10–20Hz | 扇区化减速、**横移绕行**（麦轮优势）、贴边行驶 | V1 + V2 风险扇区 | 高 |
| **L3 规划层** | 1–5Hz | waypoint 巡线 + 局部代价地图（轻量 VFH / 势场法） | 定位 + L2 汇总 | 中 |
| **L4 语义层** | 低（按需） | 人/宠物识别与避让（**非安全兜底**） | 摄像头（**依赖 S2-P 预研**） | 补充 |

**与 TOF 方案的关键差异（必须知道）**

| | TOF 方案 | **纯视觉方案** |
|---|---|---|
| L1 的物理量 | 距离（mm） | **TTC（秒）** |
| L1 频率 | 100–1000Hz | **10–20Hz（受帧率与 CPU 限制）** |
| 近距盲区 | 小 | **较大（< 10cm）** |
| 暗光 | 可用 | **不可用** |
| 静止时 | 可用 | **不可用**（需 V3 扫视缓解） |
| 速度上限 | 可较高 | **必须更低（首版 ≤ 0.15–0.2 m/s）** |

**麦轮是重要优势**：遇到障碍可以不减速直接**横向平移**让开，比差速底盘动作更自然。

## 四、架构设计

### 4.1 模块划分（落在 `wo-bot-control`）

```
src/modules/navigation/            ← 新建
├── odometry.py          里程计：编码器 + IMU 融合 → (x, y, θ, v, ω)
├── safety.py            安全仲裁：反射层急停、看门狗、失效策略（最高优先级）
├── avoidance.py         避障：感知扇区 → 限速/绕行矢量
├── planner.py           航线规划：waypoint 执行、到点判定、局部绕障
├── mode_manager.py      模式状态机：manual / semi / auto 与接管规则
├── perception/          ← 纯视觉感知（当前主路线）
│   ├── base.py              感知源抽象：统一输出「扇区风险 / TTC / 可通行区域」
│   ├── looming.py           V1 光流发散 → TTC（IMU 陀螺补偿旋转）
│   ├── ground_plane.py      V2 地面平面几何 → 自由空间 + 低矮障碍/落差
│   ├── active_scan.py       V3 云台扫视 → 运动视差远近排序
│   └── calibration.py       相机标定参数（内参、安装高度/俯仰）
├── sensors/             ← 可选增强（TOF/超声，架构预留，未接入前不启用）
│   ├── base.py              测距传感器抽象（可插拔：TOF / 超声 / 雷达）
│   ├── tof_vl53l1x.py       I2C TOF 驱动（待硬件）
│   └── ultrasonic.py        GPIO 超声波驱动（待硬件）
└── fusion.py            多源融合：视觉（无绝对距离）+ 测距（如有）→ 统一风险扇区
```

> **设计要点**：`perception/base.py` 与 `sensors/base.py` 输出**同一种"风险扇区"结构**，
> 因此纯视觉与 TOF **可以互换或叠加**，将来加装 TOF 只需新增一个 source，不改上层。

复用现有：
- 执行 → `motion/controller.py` 的 `set_mecanum_velocity` / `stop` / `emergency_stop`
- 通信 → `motion/hardware.py` 的 `RosmasterHardware`（串口线程已就绪）
- **取帧 → `vision/camera.py` 的 `get_frame(camera_id)`（已返回 numpy BGR 帧，可直接做 CV）**
- **云台 → `motion/gimbal.py` 的 `set_angles` / `move_pan_tilt`（V3 主动扫视用）**
- 上报 → `system/collector.py`（新增 odom / imu / 避障状态字段）

### 4.2 数据流

```
                       ┌──── safety.py（反射层，独立协程，最高优先级）────────────┐
感知（视觉 V1 / TOF）──►│  TTC < 阈值 或 距离 < 阈值 → 直接 controller.stop()     │
                       └────────────────────────┬──────────────────────────────┘
                                                │ 覆盖/否决
编码器 + IMU ──► odometry.py ──(x,y,θ)──► planner.py ──(vx,vy,vz 期望)──► avoidance.py ──► controller.set_mecanum_velocity
     │                 │                      ▲                                  ▲
     │                 └──► collector 上报    └── waypoint 航线（来自 Web 端）    │
     └──► looming.py（陀螺补偿旋转）──────────────────────────────────────────────┤
摄像头 ──► ground_plane.py（V2）──────────────────────────────────────────────────┤
云台 ──► active_scan.py（V3，停车/起步前扫视）────────────────────────────────────┘
```

### 4.3 协议扩展（草案）

| 消息 | 方向 | 说明 |
|---|---|---|
| `control_mode_set` / `control_mode_ack` | 前端 → 服务端 | 切换模式（**需鉴权**，见安全） |
| `control_mode_status` | 服务端 → 前端 | 当前模式、是否被安全层降级、降级原因 |
| `waypoint_list_set` / `waypoint_list_get` | 双向 | 航线增删改查 |
| `cruise_start` / `cruise_pause` / `cruise_resume` / `cruise_stop` | 前端 → 服务端 | 巡航控制 |
| `cruise_status` | 服务端 → 前端 | 当前航点、剩余距离、进度、避障事件 |
| `odometry_status` | 服务端 → 前端 | `(x, y, θ)`、速度、定位置信度 |
| `range_status` | 服务端 → 前端 | 各方向测距值（用于 Web 端可视化） |
| `avoidance_event` | 服务端 → 前端 | 触发减速/绕行/急停的事件与原因 |

> 状态类消息统一走现有的状态广播周期（复用 `collector` 的推送通道），避免高频刷屏。

## 五、模式定义与职责边界

### 5.1 权威定义

| | **manual** | **semi** | **auto** |
|---|---|---|---|
| 方向来源 | 摇杆 | 摇杆（人的**意图**） | 航线规划器 |
| 速度上限 | 人给多少给多少 | 避障层**可下调** | 规划器统一限速 |
| 避障动作 | 仅 L1 急停 | L1 急停 + L2 减速/横移绕行 | L1 + L2 + L3 局部重规划 |
| 会自己选路吗 | 不会 | **不会**（只做让开，不改变前进方向） | 会（在航线附近重规划） |
| 失效/超时 | 停车 | 停车 | 停车 + 上报 |

### 5.2 状态机与接管规则

- `manual → semi/auto`：需要显式请求 + **确认**（UI 二次确认，防止误触）
- `auto ⇄ semi`：允许直接切换；`auto → semi` 时**保留当前位置**，方向权立即交还给人
- `任意 → manual`：**立即生效**，机器人停车并把控制权交还（最高优先级，不受安全层阻塞）
- **安全层降级**：`semi/auto` 期间若触发多次急停或传感器失效 → 自动降级到 `manual` 并
  通过 `control_mode_status` 广播原因（**降级必须让用户知道**，不能静默）

## 六、安全设计（本方案的核心）

> 自主运动是**唯一可能造成物理损伤**的功能，安全设计先于功能。

| 层级 | 机制 | 触发 | 动作 |
|---|---|---|---|
| S1 | 反射层急停 | **TTC < 阈值**（纯视觉）或距离 < 阈值（有 TOF 时） | 立即 `stop()`，最高优先级 |
| S2 | **感知失效** | ① 读不到帧 / 帧率骤降<br>② **画面过暗**（亮度低于阈值 → 视觉原理性失效）<br>③ 可用特征点过少（纯白墙/玻璃）<br>④ 传感器值异常（0 或超量程） | **一律按"有障碍"处理**（fail-safe）：停车 + 广播"感知不可用"。<br>**暗光下必须禁止 auto**（而非冒险继续） |
| S3 | 决策层看门狗 | 决策协程 > 500ms 未心跳 | 停车 + 上报 |
| S4 | 通信失联 | 前端 WebSocket 断开 | 停车（不继续自驾） |
| S5 | 电池低压 | 电压 < 阈值（复用 `power_policy`） | 停止巡航 → 就近停靠 + 提示 |
| S6 | 姿态异常 | IMU 倾角超阈值 / 加速度冲击 | 停车（疑似跌落/被搬动） |
| S7 | 堵转/顶死 | 编码器反馈与指令长期不符 | 停车 + 反转脱离（可配置） |
| S8 | **TTC 误判兜底** | TTC 估计突变/不可信（光流质量低） | 降速到 crawl 速度；连续 N 帧不可信 → 停车 |

**默认关闭**：`semi/auto` 默认禁用，需在配置中显式开启并在 UI 二次确认。
**一键急停**：UI 已存在，本方案把它接到 `emergency_stop()` 并保持最高优先级。
**纯视觉特有的一条铁律**：**"看不见" ≠ "没有障碍"** —— 任何感知不确定都必须倾向于停车。

## 七、风险与未决问题

| ID | 风险/问题 | 影响 | 对策 |
|---|---|---|---|
| R1 | 麦克纳姆轮里程计漂移 | 巡航偏差累积 | 保守速度、短航程、手动校正点；不承诺长期定位 |
| R2 | **纯视觉在暗光下原理性失效**（机器人无红外补光） | 暗处完全不可避障 | 亮度检测 → **暗光禁止 auto / 强制 crawl**；长期可加红外补光或 TOF |
| R3 | **无 GPU 推理通路**（无 TRT/onnxruntime、OpenCV 无 CUDA） | 语义检测（V4）与学习式深度不可用 | 当前走经典 CV（V1–V3）；若需 V4，先做 **S2-P 技术预研** |
| R4 | 视觉误报/漏报 | 误刹或碰撞 | **纯视觉方案下不再有 TOF 兜底** → 以"更大安全余量 + 更低速度 + fail-safe 停车"换取；验收按 TTC/停车距离考核 |
| R5 | CPU 已 70%，视觉处理叠加算力 | 影响视频/控制实时性 | 低分辨率处理（160×120）、稀疏光流、降频；回收 `compiz` 算力（**¥0 收益最大的一步**） |
| R6 | Rosmaster 固件能力未知 | 编码器精度/堵转反馈可能不足 | S0 先实测编码器分辨率和一致性 |
| R7 | 单目 TTC 对**纯旋转**敏感 | 原地转向时误判 | 用 IMU 陀螺补偿旋转分量（本机具备，是纯视觉路线的关键前提） |
| U1 | 40-pin 可用引脚 | 决定将来 TOF 能否接入 | 不阻塞纯视觉路线；将来加装时再确认 |
| U2 | 是否加装 TOF（¥50–90） | 补暗光 + 近距盲区 | **可选增强**，不阻塞当前路线 |
| U3 | 巡航的安全责任边界（人在不在场） | 影响速度/兜底策略 | **纯视觉方案下建议：首版 auto 必须有人在场** |
| U4 | 首版速度上限定多少 | 直接决定安全性 | 建议 ≤ 0.15–0.2 m/s，随实测逐步放宽 |
