# 硬件诊断体系设计（开机自检 + 实时诊断 + 面板）

> 动机：本次电机故障排查耗时两天，暴露的根本问题是——**硬件状态没有统一观测**。
> 一个轮子被固件刹车，表现为"能动但不动"，只能靠人眼猜；
> 编码器冻结、IMU 全零、电池读数可疑，都是靠零散日志偶然发现的。
> 目标是：**任何硬件异常，都能在面板上一眼看出来，并自动区分"坏了"还是"没接"还是"数据链断了"**。

## 1. 架构

```
        ┌───────────── DiagnosticsRegistry ─────────────┐
        │  每个硬件 = 一个 Check，统一接口：             │
        │     name / run(readonly) -> CheckResult       │
        │     CheckResult: ok|warn|fail, detail, data   │
        └───────────────┬───────────────────────────────┘
                        │
     开机：run_all()  ──► 自检报告（写日志 + 广播一次）
     运行：run_fast() ──► 实时状态（~1Hz 广播）
                        │
                   WS: hw_diagnostics
                        │
                   前端诊断面板
```

**关键设计原则**
1. **只读优先**：开机自检**不驱动任何执行器**（动轮子/云台要人确认）。需要驱动的检查单独归入"主动自检"，必须显式触发。
2. **区分三类故障**（这是本次教训的核心）：
   - `fail_hw`：硬件本身坏（如轮子卡滞）
   - `fail_link`：数据链断（如编码器/IMU 冻结、串口死）
   - `fail_cfg`：配置/软件问题（如摄像头 id 选错、阈值不合理）
3. **诊断不控制**：只报告，处置交给安全层。
4. **可逐项启用**：每项检查独立开关，避免一个检查拖慢整个循环。

## 2. 检查清单（按优先级）

### P0 已有基础，直接接入
| 检查 | 手段 | 判据 | 本次价值 |
|---|---|---|---|
| **轮子/编码器** | 已有 `wheel_health.py` | 有指令无增量 → stall；全冻结 → link | ✅ 直接命中本次故障 |
| **IMU** | `odometry.get_imu()` | 陀螺+加速度全 0 → 无硬件 | ✅ 证实"没有陀螺仪" |
| **串口链路** | Rosmaster bot 读取是否成功、数据是否刷新 | 连续 N 次读失败/冻结 → link | ✅ 区分"链路死"与"电机坏" |
| **摄像头** | `camera_manager.get_frame()` | 无帧 → 报 ERROR 并**自动切换**另一路 | ✅ USB 掉线那次 |
| **云台** | 方法存在性 + 状态可读 | 缺 `set_pan` → fail_cfg | ✅ 曾因方法名错导致云台不动 |

### P1 系统级（复用现有 healthcheck.sh 的能力）
| 检查 | 判据 |
|---|---|
| 磁盘 | 使用率 > 85% warn，> 92% fail（**当前 90% warn**）|
| 内存 | 可用 < 200MB warn |
| CPU 温度/频率 | 过热降频 warn |
| systemd 服务 | 关键服务非 active → fail |
| apt/dpkg 元数据 | 存在全 NUL 文件 → warn |
| 网络 | Wi-Fi 信号强度、网关可达性 |

### P2 外设
| 检查 | 判据 |
|---|---|
| 音频 | USB 声卡存在、ALSA 混音器可读 |
| 电池 | 电压读数合理性（**本次 4.70V 恒定可疑 → 应能报"读数不可信"**）|
| DHT11 温湿度 | 读数超范围 → warn |
| 红外接收 | 设备存在 |
| 测距（TOF/超声） | 不存在 → 明确标注（影响避障方案选择）|

### P3 运行时
| 检查 | 判据 |
|---|---|

| AI 运行时 | onnxruntime / tensorrt / torch 是否存在 |
| 摄像头格式 | MJPG/YUYV 支持情况（影响帧率）|

## 3. 数据结构

```python
@dataclass
class CheckResult:
    name: str                 # "轮子 m4"
    kind: str                 # motor / imu / camera / serial / battery / disk ...
    status: str               # ok | warn | fail
    failure_class: str | None # hw | link | cfg（fail 时必填）
    detail: str               # 人类可读原因
    data: dict                # 面板展示用（如增量、帧率、电压）
```

自检报告：`{"ts":..., "overall": "ok|warn|fail", "checks": [CheckResult...]}`
实时状态：同上，只含 fast checks（~1Hz）

## 4. 面板设计

```
┌─ 硬件诊断 ──────────── 总体: ⚠ 1 项异常 ─┐
│ 🔴 轮子 m4   stall   hw     Δ0 / 其它 Δ3100 │
│ ✅ 轮子 m1-m3  ok                          │
│ ⚠️ IMU      无数据   hw     全 0（疑似无硬件）│
│ ✅ 摄像头    ok      30fps  640x480        │
│ ✅ 云台      ok      set_pan 可用           │
│ ⚠️ 电池      读数可疑  link   恒定 4.70V     │
│ ⚠️ 磁盘      90%      cfg    剩 5.6G        │
│ ✅ 串口      ok      数据在刷新              │
└──────────────────────────────────────────┘
   开机自检: ✅ 6 项通过 / ⚠ 2 项警告 / 🔴 0 项失败
```

## 5. 实施顺序

1. **框架**：`DiagnosticsRegistry` + `CheckResult` + 自检/实时两档 + WS 广播
2. **P0 五项接入**（轮子/IMU/串口/摄像头/云台）—— 其中轮子与能力探测已写好，接上即可
3. **面板**：前端诊断卡片（复用 WS 消息）
4. **P1 系统级**（把 healthcheck.sh 的判据搬到 Python，与面板统一）
5. **P2/P3 外设与运行时**
6. 每项都配单测；`fail_hw` / `fail_link` / `fail_cfg` 分类必须有测试覆盖

## 7. 通用性要求（**不可固化任何具体机型**）

这是本设计最重要的一条约束：**这是通用系统，只支持一种机型就是失败**。

| 不可固化的东西 | 正确做法 |
|---|---|
| **轮子数量** | 由 **驱动类型** 决定：`mecanum`=4（全向）、`differential`=2、`ackermann`=4（2 驱动+2 转向）；轮名由硬件抽象层给出，不在诊断里写死 `m1..m4` |
| **编码器数量/名称** | 由硬件后端声明；读不到就报"该机型无编码器"，而不是报故障 |
| **电池配置**（电压阈值/电芯数）| 来自配置（`battery.enabled` / `min_voltage` / `max_voltage`）；未配置则显示"不适用"，**不得假定 12V 10.5V** |
| **外设清单** | 以 `PeripheralRegistry`（peripherals.yaml）为准动态枚举；没有 DHT11/红外不算故障 |
| **测距/IMU 等** | 存在就检查活性，不存在按"该机型不支持"标注，不报 fail |

**判定原则**：
- `fail` 只用于"**该机型声称有、但工作不正常**"的东西
- "**该机型没有**" 一律是 `ok/不适用`，不是故障
- 诊断项应当是**数据驱动**（遍历实际存在的设备），而不是遍历代码里写死的常量

2. `_hw_checks` 写死四轮
3. 电池检查写死 `10.5V`
4. `Odometry.get_raw_encoders()` 固定返回 m1..m4 四元组

## 8. 执行器自检（通用方案，不只云台）

### 为什么需要它
被动监测只能证明"**没坏**"，不能证明"**能按指令动**"。
本次电机故障就是例子：静止时四轮都"正常"，只有给它指令才发现有个轮子不动。
所以执行器需要一个**主动**自检：发一条已知指令，验证它真的执行了。

### 通用四阶段模型（所有执行器共用一个骨架）

```
1. 保存状态   → 记录当前姿态/位置/亮度，供恢复
2. 发已知指令 → 幅度小、方向明确、可重复
3. 测量反馈   → 按机型能力自动择优（见下表）
4. 恢复原状态 → 必须执行（finally），否则会把设备留在测试姿态
```

### 反馈来源（按能力自动择优，这是"通用"的关键）

| 优先级 | 反馈类型 | 适用 | 说明 |
|---|---|---|---|
| 1 | **角度/位置回读** | 带反馈的舵机、编码器电机 | 最直接，可直接断言"到位误差" |
| 2 | **视觉反馈** | 云台、可动摄像头 | 无角度反馈时用相机：指令前后各拍一帧，计算图像位移；**位移非同零 = 真的动了** |
| 3 | 电流/温度 | 有采样能力时 | 可判堵转/过载 |
| 4 | 人工确认 | 蜂鸣器/LED 等无回读设备 | 由面板提示"请确认是否听到/看到" |

> **视觉反馈这一条是通用方案的支点**：任何"带着相机动的东西"（云台、升降、转向）
> 都可以用图像位移来验证，不需要额外传感器。

### 统一接口与注册表

```python
class ActuatorSelfTest(Protocol):
    name: str                 # "云台 pan/tilt"
    risk: str                 # "low"（微动）/ "medium"（会移动整机）
    requires: list[str]        # ["gimbal", "camera"] —— 能力不满足则跳过并说明
    async def run(env) -> SelfTestResult   # 内含保存/指令/测量/恢复

# 注册表：新增机型/新增执行器 = 加一条，不改框架
SELF_TESTS = {"wheels": WheelSelfTest(), "gimbal": GimbalSelfTest(), "buzzer": BuzzerSelfTest()}
```

`SelfTestResult`：`{name, ok, steps:[{cmd, measured, ok, note}], detail, restored: bool}`

### 具体设计：云台自检

**有角度回读时**（首选）
```
回中 → 读角度(期望 90°±3°) → pan +20° → 读角度 → pan -20° → 读角度 → tilt +15° → 读角度 → 回中
判据：每一档回读与指令之差 < 容差；且方向一致
```

**无角度回读时**（本项目云台可能属于此类）—— 用相机验证
```
1. 回中，抓帧 A
2. pan += 20°，等 settle（0.5s），抓帧 B
3. 用相位相关/特征匹配求 A→B 的**水平位移**
4. 判据：|位移| > 阈值（例如 >8px）证明真的动了；符号与指令方向一致
5. 反向再来一次（pan -= 20°），确认可逆、无卡滞
6. tilt 同理（垂直位移）
7. finally：回中
```
**这条判据能抓到的故障**：舵机线松动（指令成功但图像不动）、机械卡滞（位移为 0）、
方向接反（位移符号与指令相反）、行程不足（位移明显小于预期）。

### 风险分级与约束（必须写进实现）

| 约束 | 说明 |
|---|---|
| **只能显式触发** | 绝不开机自动跑（会动）|
| 幅度小、可重复 | pan ±20°、tilt ±15°；轮子 24cm |
| 单步超时 + 总超时 | 避免卡死主循环 |
| **finally 恢复** | 云台回中、轮子停 |
| 结果要广播 | 面板显示每一步的"指令 vs 实测" |
| 按能力跳过 | 缺云台/相机 → 跳过并说明"该机型不支持"，**不报故障** |

### 当云台扫视已在使用时
扫视（V3）本身就在动云台，但那是**为了看环境**，不是**为了验证自己**。
两者可复用同一套"移动-停稳-测量"原语，但**语义不同**：
自检关心"云台是否听话"，扫视关心"环境是否空旷"。不要混用，否则自检结论会被环境干扰。
